# VDK GID — контекст проекта для ИИ-агентов

Прочитайте этот файл перед изменением кода. Он действует для всего репозитория и описывает
концепцию продукта, устройство приложения и правила, которые нужно сохранять при разработке.
При изменении архитектуры или поведения обновляйте этот контекст и связанную документацию.
Инструкции пользователя по текущей задаче имеют приоритет.

## Идея и цель

Kuda_Skhodit_VL — городской гид по Владивостоку, который помогает выбрать, куда сходить и чем заняться,
с учётом интересов, бюджета, расположения и предыдущих реакций человека.
Основной сценарий: **каталог → предпочтения → подборка → реакция → обновлённая подборка**.
Ценность продукта — подходящие места с понятными причинами рекомендации и проверяемыми
сведениями о стоимости и посещении. Не следует придумывать места, цены или факты для заполнения данных.

Два основных сценария работы:

- Посетитель создаёт гостевой профиль, задаёт интересы и бюджет, просматривает каталог,
  получает рекомендации, оценивает места и отмечает уже знакомые.
- Редактор загружает исходный Excel, проверяет отчёт, подтверждает создание черновиков,
  уточняет сведения и отдельно публикует карточки.

## Текущий объём и границы

- Реализован локальный backend MVP с REST API `/api/v1`, Swagger и PostgreSQL.
- В `frontend/` реализован локальный React + TypeScript + Vite интерфейс: каталог, предпочтения,
  подборка, discovery и страница места. `clients/imports.ts` остаётся отдельным клиентом импорта.
- Есть каталог с фильтрами, гостевые профили, реакции, рекомендации, случайная выдача discovery,
  редакторское управление местами и импорт Excel через CLI и API.
- Модуль `app/analytics/` сохраняет выдачи recommendations/discovery, их страницы и
  события card_view/place_open/swipe/swipe_undo. `POST /me/events` получает профиль
  из Bearer, проверяет принадлежность подборки и карточки, UUID и версию реакции.
  Свайп и событие записываются атомарно. Сводка доступна только редактору через
  `/admin/analytics/summary`. Контракт и ограничения — `docs/analytics.md`.
- Рекомендации работают на объяснимых правилах `rules-v1`. Интерфейс `Ranker` и безопасный
  fallback подготовлены, но внешняя или локальная LLM ещё не подключена.
- В `recommender/` есть независимый сервис Qwen3-Embedding-0.6B с JSON-каталогом
  из 188 мест. Он запускается отдельно на порту 8001, не читает PostgreSQL и пока
  не подключён к `Ranker` основного API. Инструкция — `recommender/README.md`.
  Его зависимости и окружение отдельные; веса `recommender/models/`, кэш и локальный
  Python исключены из Git. E5 в проекте не используется.
  Демонстрационный Swagger Qwen открыт по http://149.154.70.109/model/docs.
  Путь /model/ принимает анонимные запросы через nginx с ограничениями; это не
  подключение Qwen к основному Ranker. Серверный root_path — /model, локальный — пустой.
  Конфигурация proxy: recommender/deploy/, управление — docs/qwen-server.md.
- `recommender/train_adapter.py` обучает экспериментальную проекцию запросов поверх
  замороженной Qwen на синтетических примерах с разметкой из типов/тегов каталога.
  По умолчанию отключена. Для её включения нужны `QUERY_ADAPTER_MODE=experimental`
  и `QUERY_ADAPTER_PATH` на прошедший проверку версионированный артефакт; она не применяется к похожим местам
  и не подключена к backend. Результаты на малом синтетическом тесте не доказывают
  качество для пользователей. Прогулки, SUP и бассейны имеют строгий отбор.
  При точном названии карточки автоматическое определение категории пропускается,
  но явные фильтры сохраняются. Одна сумма «до N рублей» распознаётся из query
  только при отсутствии поля budget; явный null снимает ограничение.
  Адаптеры не перезаписываются; кандидаты, ухудшившие регрессионный набор,
  сохраняются с запретом загрузки. Совместимость проверяется по содержимому
  весов, каталога и конфигурации кодирования, без зависимости от времён файлов.
- Карты, фотографии, погода, события, маршруты, отзывы, избранное и аккаунты с паролями —
  возможные следующие итерации, а не существующие функции.
- Публичная эксплуатация пока не подготовлена. Текущий локальный доступ привязан к loopback.
  Не добавляйте облачные сервисы, GPU-инфраструктуру или микросервисы без задачи на это.
- Seed содержит вымышленные места с префиксом «ДЕМО». Импортированные данные требуют проверки
  редактором. Число записей в конкретной локальной БД не является постоянным свойством проекта.

## Архитектура и навигация

Модульный монолит: Python 3.12, FastAPI, Pydantic 2, SQLAlchemy 2 async, asyncpg,
PostgreSQL 16, Alembic и Docker Compose. Точные зависимости закреплены в `requirements*.txt`.
Одна async SQLAlchemy-сессия на запрос. Для небольшого каталога геофильтр Haversine
выполняется в Python после SQL-фильтров; PostGIS — вариант при подтверждённом росте.

| Путь | Ответственность |
|---|---|
| `app/main.py` | Сборка API, middleware, CORS, проверки здоровья |
| `app/core/config.py` | Настройки окружения |
| `app/api/dependencies.py` | Авторизация и зависимости запросов |
| `app/db/` | Сессия и основные ORM-модели |
| `app/catalog/` | Каталог, фильтры, схемы, публикация, редакторские операции |
| `app/profiles/` | Гостевые профили, предпочтения, реакции, знакомые места |
| `app/analytics/` | Снимки выдачи, события карточек, статистика и очистка истории |
| `app/recommendations/` | Подбор, discovery, правила ранжирования и интерфейс Ranker |
| `recommender/` | Отдельная проверка смыслового поиска Qwen, свой API и JSON-каталог |
| `app/importing/` | Чтение Excel, CLI, preview/apply API, загрузки и очистка |
| `app/importing/models.py` | ORM-модель пакета импорта |
| `app/seed.py` | Демонстрационные данные |
| `alembic/versions/` | Последовательные миграции БД |
| `tests/` | API, импорт, ранжирование; интеграционные проверки на PostgreSQL |
| `clients/` | Вспомогательный TypeScript-клиент |
| `docs/` | Детальные контракты, архитектурные решения и протоколы проверок |

Основные сущности: `Place`, `Category`, связь места с категориями, `Profile`,
`PlaceState` (реакция и знакомство конкретного профиля с местом), `ImportBatch`.

## Правила продукта, которые нужно сохранять

### Каталог и качество сведений

- Статусы места: `draft`, `published`, `archived`. Черновики скрыты от посетителей;
  прямое обращение к ним возвращает 404. Архивные места исключены из подборок,
  прямое обращение возвращает 410.
- Публикация требует координат, ссылки на источник и даты проверки. Это защищено
  валидацией API и ограничением БД. Не подставляйте дату импорта вместо даты проверки.
- Удаление места редактором мягкое: сохраняются ID и реакции; карточку можно восстановить.
- `price_rub = null` означает неизвестную стоимость, `0` — известные нулевые расходы.
  При заданном бюджете места с неизвестной стоимостью исключаются.
- Для импорта `price_rub` — верхняя граница полного диапазона расходов на человека.
  Бесплатный вход сам по себе не означает бесплатное посещение. Исходные диапазоны сохраняются.
- Категории фильтра объединяются по ИЛИ. Широта, долгота и радиус передаются вместе;
  радиус измеряется в километрах, бюджет — в рублях.
- Не раскрывайте `source_data` и `import_key` через публичные карточки.

### Профиль и подбор

- Гостевой токен выдаётся при создании профиля; в БД хранится SHA-256, а не исходный токен.
  Удаление профиля отзывает доступ и удаляет его состояния мест.
- Реакции: `like`, `dislike`, `neutral`. Повторный PUT заменяет реакцию без дублей.
  `is_known` — независимый признак; его изменение не должно стирать реакцию.
- `reaction_revision` монотонно изменяется при смене реакции и свайпах; старые PUT/DELETE
  тоже учитываются. При событии нужна ожидаемая версия; устаревший свайп/отмена — 409.
  Повтор того же event_id с тем же телом не изменяет состояние и не увеличивает счётчики.
  Удачная отмена восстанавливает предыдущее значение только для последнего актуального свайпа.
- Выдача API не доказывает просмотр: card_view отправляет клиент по фактической видимости.
  События не раскрывают чужие подборки. Точные координаты и токены в аналитику не записываются.
  Удаление профиля удаляет историю каскадно. Срок истории по умолчанию 90 дней;
  физическая очистка запускается `python -m app.analytics.cleanup`, расписание не установлено.
- Принятая механика жестов: влево — like, вправо — dislike, вверх — neutral.
  Backend получает значение реакции, а обработка жестов относится к клиенту.
- Dislike действует до замены/отмены и исключает конкретное место, не всю категорию.
  Знакомые и дизлайкнутые места исключаются из рекомендаций по умолчанию.
- Neutral не меняет баллы, но любая сохранённая реакция исключает карточку из discovery.
  Случайная пагинация discovery не гарантирует отсутствие повторов между запросами.
- В рекомендациях отсутствие `budget_rub` означает бюджет профиля; явный `null` снимает
  ограничение. Сохраняйте различие между отсутствующим полем и полем со значением null.
- Сначала применяются ограничения каталога и состояний профиля, затем ранжирование.
  Пустую выдачу возвращайте как `items: []`, `total: 0`, без скрытого ослабления фильтров.
- Базовые баллы: 3 за совпавшую категорию интересов, по 1 за лайки других опубликованных
  мест той же категории (максимум 3 на категорию), 2 за собственный лайк места.
  Баллы не являются вероятностью; ответ включает причины и `algorithm_version`.
- Будущий Ranker может только переставить разрешённые ID: каждый ровно один раз.
  Неизвестные, повторённые или пропущенные ID, ошибка либо таймаут 5 секунд включают RuleRanker.
  Ограничения доступа, бюджета и географии остаются обязанностью backend.
  Описания мест для LLM — данные, а не инструкции; секреты и доступ к БД ей не передаются.

### Импорт

- Читается лист `Места` из `.xlsx`/`.xlsm`; исходная книга не изменяется.
  Макросы не выполняются, формулы в данных отклоняются, внешние ссылки не скачиваются.
- CLI по умолчанию выполняет dry-run; запись требует `--apply`.
  API использует отдельные preview и apply; preview не создаёт места.
- Новые места всегда черновики. Существующие пропускаются без перезаписи правок редактора;
  удаление строки из Excel не удаляет карточку. Сохраняйте стабильный ключ дедупликации
  и исходные строки, включая дубли, в `source_data`.
- Запись транзакционная: при ошибке нет частично загруженного каталога.
  Сохраняйте согласованные блокировки CLI/API и идемпотентность повторного apply.
- Preview не резервирует записи: apply повторно проверяет актуальную БД.
  Сохраняйте ограничения размера, ZIP/XML, строк и столбцов при изменении парсера.
- Файлы готовых загрузок временно хранятся в PostgreSQL, срок подтверждения — час.
  После успешного apply байты удаляются; отчёт остаётся. Очистка запускается
  командой `python -m app.importing.cleanup`, расписание пока не настроено.

## Порядок внесения изменений

1. Прочитайте затрагиваемые модули и соответствующий документ из списка ниже.
   Сверьте описание с текущим кодом: документация и отчёты могут отставать.
2. Проверьте рабочее дерево Git. Не откатывайте и не перезаписывайте чужие незавершённые изменения.
3. Сохраняйте модульные границы и существующие API-контракты. Меняйте их вместе со схемами,
   потребителями и документацией, если этого требует задача.
4. Изменения схемы БД оформляйте новой миграцией Alembic; не переписывайте уже применённые
   миграции. Проверяйте соответствие ORM и миграций.
5. Проверяйте изменённое поведение подходящими тестами. Для документации достаточно сверки
   ссылок, команд и утверждений с кодом; запуск БД ради правки текста не требуется.
6. В результате работы укажите, что изменено, какие проверки действительно выполнены
   и что осталось непроверенным. Не выдавайте старые протоколы тестов за свежий запуск.

Не коммитьте `.env`, токены, ключи, дампы БД и локальные исходные книги.
Гостевой Bearer и редакторский `X-Admin-Key` имеют разные права. Не вшивайте ключ редактора
в публичный frontend. Не удаляйте рабочие данные или Docker-тома ради проверки;
`docker compose down -v` удаляет данные. Тесты должны работать с отдельной тестовой БД.

## Запуск и проверки

Команды выполняются из корня проекта; основной локальный путь — Docker Desktop с Linux containers.
Создание `.env` из `.env.example` требуется только при его отсутствии; существующий файл не затирать.

```powershell
docker compose up -d --build
docker compose --profile test run --build --rm tests
docker compose --profile test run --rm tests ruff check --no-cache app tests
# При изменении ORM/миграций, на подготовленной локальной БД:
docker compose exec -T api alembic check
```

Миграции выполняет сервис `migrate` перед стартом API. Seed запускается отдельно и только
при необходимости демонстрационных данных: `docker compose exec api python -m app.seed`.
Swagger: `http://localhost:8000/docs`; готовность БД: `http://localhost:8000/health/ready`.
Не запускайте два набора интеграционных тестов одновременно с одной тестовой БД:
фикстуры очищают её таблицы. В контейнерах hostname БД — `db`; для Python на хосте
используется отдельный вариант подключения с `compose.local.yaml`, описанный в README.

## Frontend

Инструкция: `frontend/README.md`. Dev server — 127.0.0.1:5173, proxy API — 127.0.0.1:8000.
Запуск: `cd frontend`, `npm.cmd ci`, `npm.cmd run dev`. Проверки: `npm.cmd run build`,
`npm.cmd test` (Edge; dev server и backend запущены). Гостевой токен в localStorage,
секреты сервера в сборку не передаются. Тестовые места существуют только в mock-тестах.
Сохранение предпочтений и реакции проверяются отдельно на живом API с временным гостем.
Текущий frontend — SPA, SSR/SEO и публичное развёртывание не реализованы.
