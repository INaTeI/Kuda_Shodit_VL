# Сбор показов и обратной связи

Реализован в основном FastAPI API `/api/v1`, не в сервисе Qwen на порту 8001.
Используется существующий локальный модульный монолит и PostgreSQL. Никакие внешние
аналитические сервисы не получают события. Фронтенда пока нет: фактические показы
должен отправлять будущий клиент. HTTP-клиент для него — `clients/analytics.ts`.

## Данные

- `recommendation_runs`: владелец, источник recommendations/discovery, версия
  алгоритма, эффективные фильтры, интересы, число всех кандидатов и серверное время.
  Точные latitude/longitude не сохраняются; радиус и бюджет остаются.
- `recommendation_items`: только карточки реально выданной страницы и их позиции
  с учётом offset (нумерация с нуля). Выдача API не считается просмотром.
- `interaction_events`: неизменяемые события, их UUID, контекст и результат изменения
  реакции. Сервер не принимает profile_id, позицию, версию алгоритма или время от клиента.
- `place_states` по-прежнему хранит текущую реакцию и независимый is_known.
  Новое поле `reaction_revision` защищает текущую реакцию от устаревших действий.

Новая миграция: `0004_analytics`. Уже применённые миграции не менялись.
`recommendation_id` добавлен в ответы POST `/recommendations` и `/discovery`.
Старые поля ответов и старые маршруты реакций сохранены.
Основной API пока не принимает свободный текст пожелания: в статистику нельзя
добавлять выдуманный текстовый запрос или приписывать ему выдачу Qwen.

## Сценарий карточки

1. Создать профиль, сохранить Bearer-токен.
2. Запросить `/recommendations` или `/discovery`; сохранить recommendation_id и items.
3. Получить `/me/place-states`; для отсутствующей строки reaction_revision = 0.
4. Когда карточка действительно видима, отправить card_view с новым event_id.
5. На открытие отправить place_open. На свайп — swipe с ожидаемой версией реакции.
6. Сохранить полученную reaction_revision. Для отмены отправить swipe_undo,
   передав event_id отменяемого свайпа и актуальную версию реакции.

Каждое событие отправляется POST `/api/v1/me/events` с Bearer-токеном.
Пример просмотра (UUID нужно заменить реальными):

```json
{
  "event_id": "a0000000-0000-4000-8000-000000000001",
  "recommendation_id": "b0000000-0000-4000-8000-000000000001",
  "place_id": "c0000000-0000-4000-8000-000000000001",
  "event_type": "card_view"
}
```

Свайп после просмотра:

```json
{
  "event_id": "a0000000-0000-4000-8000-000000000002",
  "recommendation_id": "b0000000-0000-4000-8000-000000000001",
  "place_id": "c0000000-0000-4000-8000-000000000001",
  "event_type": "swipe",
  "reaction": "like",
  "expected_reaction_revision": 0
}
```

Для отмены: event_type = swipe_undo, undo_event_id = UUID этого свайпа,
expected_reaction_revision = значение из его ответа; поле reaction не передаётся.
Отмена восстанавливает предыдущее значение, а не безусловно удаляет реакцию.
Если между свайпом и отменой реакция изменилась, отмена отклоняется с 409.

При принятом swipe или swipe_undo событие и состояние меняются одной транзакцией.
is_known не изменяется. Доступна только собственная подборка и место из её страницы.
card_view обязателен до place_open, swipe и swipe_undo. Проверка отражает сигнал клиента,
но сервер не может доказать, что человек действительно смотрел на экран.

Реакция из swipe сразу влияет на существующий rules-v1. Подключения истории к Qwen
или обучения на этих событиях пока нет.

## Повторы, офлайн и конкуренция

- Создавать UUID один раз до отправки. Хранить неизменяемое тело в очереди отдельно
  для каждого профиля. Отправлять последовательно, сохраняя порядок view → swipe.
- Повтор с тем же UUID и телом возвращает 200 и duplicate=true; состояние не меняется.
  После более новых действий этот ответ всё ещё описывает исходное событие.
  Не перезаписывайте им новое локальное состояние; при сомнении получите place-states.
- Тот же UUID с другим телом: 409. Чужая/неизвестная подборка: 404.
- Устаревшая expected_reaction_revision: 409. Обновить состояния и дать пользователю
  повторить решение; не подменять версию в старой офлайн-команде автоматически.
- Сетевая ошибка/5xx: оставить тот же UUID в очереди. 401: остановить отправку,
  не переносить очередь в другой профиль. 404/410: старый контекст больше не пригоден.
- Параллельные записи одного профиля сериализуются блокировкой его строки.
  Совпадение UUID между разными профилями также даёт конфликт, а не частичную запись.
- Старые PUT/DELETE реакций работают, повышают revision при реальном изменении,
  но не создают искусственную историю показов/свайпов. Новый интерфейс карточек должен
  вызывать `/me/events`, не дублировать свайп старым PUT.

## Просмотр статистики

GET `/api/v1/admin/analytics/summary?days=7`, нужен X-Admin-Key.
Ответ: runs, empty_runs, issued_cards, card_views, viewed_cards, place_opens,
swipes, likes, dislikes, neutrals, swipe_undos.

`card_views` считает все принятые события просмотра; `viewed_cards` — уникальные пары
подборка/место за период. Повторная доставка одного event_id счётчики не увеличивает.
likes/dislikes/neutrals — события, включая впоследствии отменённые; это не текущие
предпочтения. Отмены считаются отдельно. Выдачи ограничиваются временем создания,
действия — временем получения. Свайп на старой подборке может попасть в новый период:
отношения счётчиков не следует автоматически называть конверсией одной когорты.

## Хранение и удаление

По умолчанию история доступна 90 дней, настройка `ANALYTICS_RETENTION_DAYS` (1–365).
На истёкшую подборку endpoint возвращает 410 даже до физической очистки.

```bash
python -m app.analytics.cleanup
# В контейнере:
docker compose exec api python -m app.analytics.cleanup
```

Команда удаляет старые подборки, выданные карточки и их события. Текущие предпочтения
остаются. Автоматическое расписание не установлено: на сервере нужно запускать очистку
регулярно. Удаление `/me` немедленно удаляет всю историю профиля каскадно.
Bearer-токены, IP, device fingerprint и точная геопозиция в аналитические таблицы
не записываются. Админский ключ нельзя передавать в браузерный клиент.

## Проверка и границы MVP

Проверки: snapshot выдачи, пустая выдача, discovery, позиции, изоляция, валидация,
повторы, атомарные свайпы/отмена, устаревшие версии, конкурентные записи и очистка.
Интеграционные тесты работают только с отдельной PostgreSQL vdk_test.

Это локальная реализация в существующей архитектуре, не production-обязательство:
прогноз QPS и read/write ratio не измерены, production SLO и его владелец не утверждены.
Сохраняются предварительные цели проекта: p50 <100 мс, p95 <300 мс, p99 <500 мс,
99.5% доступности, RPO 24 ч, RTO 4 ч — они не подтверждены измерениями.
Управление нагрузкой, публичная защита от массового создания профилей/событий,
восстановление резервных копий и интерфейс карточек требуют отдельной проверки перед запуском.
